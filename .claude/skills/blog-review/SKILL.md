# blog-review

ブログ執筆ワークフローの第3〜4段階の間、通し読み推敲（`/blog-writing` の通し読みモード）が済んだ後に挟む、**内容の客観チェック**専用スキル。

## 目指すゴール

書き手（本人と、執筆を手伝ってきた AI）は記事の意図や前提に馴染みすぎていて、内容の抜け・矛盾・説明不足に気づきにくい。このスキルは、会話の経緯を持たない独立したサブエージェントに記事だけを読ませることで、書き手が見落とした内容面の欠陥と、記事の良さを客観的に本人へ返す。文体・リズム・用語ブレなど「書き方」の推敲は扱わない。それは `/blog-writing` の通し読みモードの役割。

観点そのものと参考文献は docs/review-policy.md を正とする。

## 観点を 3 エージェントに分割する理由

1 エージェント・1 回のレビューでは、その回では拾わなかった指摘が、もう一度読んだときに新しく見つかることがある。これは観点を絞らずに広く読ませるほど起きやすい。そこで docs/review-policy.md の観点を 3 つの担当領域に分割し、独立したサブエージェントにそれぞれ狭い範囲を深く見てもらう。各エージェントが見る範囲を絞ることで、1 エージェントに全観点を任せた場合より見落としを減らす。

## 入力

- 引数: `{slug}`
- 読み込み: `works/{slug}/article.md`（`articles/` へ移動済みなら該当ファイル）

## 進め方

1. レビューの目的を確認する（1 メッセージ）
   - note 記事の要点「目的によってレビューの内容は全然変わる」に従い、まず本人に「今回いちばん気にしたいこと」を聞く（例: 初めて読む人に伝わるか／論理に穴がないか／期待される内容が揃っているか）
   - 答えがなければ「下記の観点一式で一般的な客観チェックを行う」旨を伝えて進める

2. 3 つの観点別サブエージェントを並列で起動する
   - docs/review-policy.md の観点を次のように 3 エージェントへ割り振る。Agent A は「内容の整合性・記事の意図」、Agent B は「根拠と論証」、Agent C は「読者への価値」を担当する
   - Agent ツール（`general-purpose`）を 1 メッセージ内で 3 回呼び、並列に起動する。3 つとも Foreground（`run_in_background: false`）で受け取る。結果をすぐ統合して提示するため
   - 各エージェントには記事本文だけを渡す。会話のここまでの経緯・著者の意図は先に説明しすぎない（染まっていない視点を保つため）
   - 渡す前提は「これはブログ記事の下書きで、著者はレビュー結果を見て修正するか判断する。担当する観点について良い点・悪い点を具体的に指摘してほしい」の 1 点。加えて、本人が 1. で挙げた最優先観点（あれば、全エージェント共通で伝える）と、docs/review-policy.md の担当節 1 つのみを渡す
   - 他のエージェントの担当観点には触れないよう指示する

3. 3 エージェントの結果を統合する
   - 同じ箇所を指す指摘が複数エージェントから出ていれば 1 件にまとめる
   - 良い点はまとめて先に伝える（モチベーション維持のため）

4. 統合した指摘を 1 件ずつ提示する（`/blog-writing` の通し読みモードと同様、**1 回のメッセージにつき 1 件**）
   - 各指摘について、本人と「反映する／今は見送って todo.md へ／不要」を決める
   - 的外れな指摘は鵜呑みにしない。本人が「これは違う」と判断したら理由を添えて棄却してよい
   - 修正は合意してから反映する。このスキル自身は文体を直さない（直す場合は `/blog-writing` の観点に委ねる）

5. 記録
   - 指摘・良い点・対応方針を `works/{slug}/review.md` に記録する（テンプレート参照）
   - 「見送り」判断がついた指摘は `works/{slug}/todo.md` にも転記する（無ければこの回に作る）

## テンプレート

`works/{slug}/review.md` の雛形。レビューは同じ記事に何度も走るので、**回ごとの節を新しい順に上へ積む**。過去の回は書き換えず、そのまま残す。

```markdown
# {slug} レビュー記録

## YYYY-MM-DD

- 実施日: YYYY-MM-DD
- 今回の観点: <!-- 1. で確認した最優先観点。なければ「一般的な客観チェック」 -->

良かった点は次のとおり。

-

指摘と対応は次のとおり。

| 重要度 | 該当箇所 | 指摘 | 対応                    |
| ------ | -------- | ---- | ----------------------- |
|        |          |      | 反映 / todo へ / 見送り |

補足。

- <!-- 反映・見送りの件数、次の回に引き継ぐこと、気づいたパターンなど -->

<!-- 以下、過去の回が続く -->
```

書き方の決まりは 2 つ。

- 回の見出しは `## YYYY-MM-DD` のみ。同じ日に 2 回走ったら `## YYYY-MM-DD（2回目）` のように回を足す
- 節の中で「良かった点」「指摘」「補足」に H3 を使わない。回を重ねると同じ見出しが並んで markdownlint の MD024（見出しの重複）に当たるため、上記のようにリード文でラベルする。太字ラベルも MD036 に当たるので使わない

## 重要原則

- 文体・リズム・用語ブレは扱わない。気づいても `/blog-writing` の通し読みモードへ差し戻す
- サブエージェントには記事の本文以外の前情報を渡しすぎない。第三者視点を保つのが目的
- 各エージェントには担当する 1 観点セットだけを渡す。観点を混ぜると、狙った見落とし防止効果が薄れる
- 1 回で全部消化できなくてよい。残りは todo.md へ逃がして次回に回す

## 次のステップ

- 見送った指摘が todo.md に残っている旨を伝える
- 客観チェックが済んだら `/blog-publish {slug}` で公開作業に進めると伝える
