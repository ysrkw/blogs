# improvements

blog システム全体への改善提案ログ。対象はスキル（blog-\*）に限らない。

- スキル（`.claude/skills/**/SKILL.md`）
- ドキュメント（`docs/writing-policy.md` / `docs/structure.md` / `docs/templates.md` など）
- ワークフロー・命名規則・運用ルール
- **振り返りの仕組みそのもの**（retrospective / notes の構造）

「どのスキルを直すか」ではなく「次のセッションが楽になるよう、この blog システムのどこを変えるとよいか」を溜める場所。各提案は対象ファイルを明記する。
`/retrospective` が追記する。

**この一覧に載るのは未適用の提案だけ**。ステータスのフラグは持たない。ユーザーが採用と判断したらその場で対象ファイルを編集し、この項目を削除する。却下したときも項目を削除する。採否とその理由は commit メッセージに書き、経緯は git 履歴で辿る。

### 2026-09-26: blog-writing - 数字を一次データで裏取りする手順を足す

- 対象: `.claude/skills/blog-writing/SKILL.md`（執筆モード 3. H2 セクションを書く）
- 背景: roi-thinking-for-engineers で、本人の記憶の数字を gh で CI の記録と突き合わせた。Prettier は記憶と実測がずれていた。本人言「実測で書けたのは良かった、可能なら標準にしたい」。現行の手順には、数字の裏取りの一手がない
- 変更案: 3. に「一次体験の数字が記憶ベースのときは、ログ・CI・請求などの一次データで確かめられないか本人に聞く。取れたら、比べた期間と条件を本人に示してから本文に使う」を足す。外部に出せない固有名（リポジトリ名など）は本文に出さないことも併記する
- 期待される効果: 断定の根拠が執筆の段階でそろい、review で根拠不足を指摘される前に潰せる

### 2026-09-26: docs/writing-style.md - 禁則表に but 構文の確認を足す

- 対象: `docs/writing-style.md`（禁則の表）、`.claude/skills/blog-writing/SKILL.md`（通し読みの準備の「6 項目」の記述）
- 背景: 1つめの H2 で「主張→ただ／でも」の流れを本人が差し戻した。今回は「避けたい言い回し」に書いたが、禁則表に載せないと通し読みで機械的に確認されない
- 変更案: 禁則表に「主張→逆接の but 構文を避ける｜『ただ』『でも』『しかし』で始まる文を grep し、理由→結論の順に直せるか読む」を足す。blog-writing の「6 項目」を「7 項目」にする
- 期待される効果: AI が書いた初稿に残りやすい英語的な流れを、通し読みの準備で拾える

### 2026-09-26: blog-outline - 寝かせた idea は経過期間の一次体験を先に聞く

- 対象: `.claude/skills/blog-outline/SKILL.md`（1. コンセプトの再確認）
- 背景: roi-thinking-for-engineers は idea から4か月あけて outline に入った。寝かせている間の体験を聞くと4件が加わり、軸が3回動いた。今回は AI が process-notes の「レビューの穴」の知見から自発的に聞いたが、手順には書かれていない
- 変更案: 1. に「idea.md の `created` から時間があいている場合は、その間に起きた一次体験と構想の変化を聞く。軸が動いたら outline 内で再定義する」を足す。再定義のたびにコンセプトを言い直して確認する
- 期待される効果: 寝かせた記事ほど増える新しい体験を、draft や review より前に取り込める

### 2026-09-26: blog-outline - テンプレートに参照先の節を足す

- 対象: `.claude/skills/blog-outline/SKILL.md`（テンプレート）
- 背景: outline で出典を2件確認し、中心語の定義の出典と流れの補強に役割を分けた。テンプレートに置き場がなく、「参照先」の節を独自に足した
- 変更案: テンプレートの「まとめで伝えたいこと」の後に「参照先」節を足す。各出典に、確認した要旨と記事での役割（定義／補強など）を1行ずつ書く
- 期待される効果: draft で出典を探し直さずに済む。中心語が出典に実際に出てくるかの確認も、outline の段階で済ませられる

### 2026-07-28: docs/templates.md - 回を重ねる記録ファイルの見出し規約を一般化する

- 対象: `docs/templates.md`、`.claude/skills/retrospective/SKILL.md`（session-logs の雛形）
- 背景: review.md が MD024（見出しの重複）に当たり、回ごとの節を `## YYYY-MM-DD` で積み、中のラベルを H3 でなくリード文にする形へ直した。同じ問題は session-logs にもある。今日は同じ slug で2セッション走った。既存ファイルへ追記すると H2 が重複するため、`-2` を付けた別ファイルにした
- 変更案: 回を重ねて追記する記録（review.md・振り返りメモ）の見出し規約を、templates.md に1節として立てる。review.md と session-logs の雛形からはそこを参照させる。session-logs は1セッション1ファイルのままとし、同日2回目のファイル名規則（`-2` など）を明記する
- 期待される効果: 次に別の記録ファイルを足すときも同じ罠を踏まない。lint を緩める判断が再発しない

### 2026-07-28: blog-review - 修正案を記事の主題と照合するステップを足す

- 対象: `.claude/skills/blog-review/SKILL.md`（指摘を提示するステップ）
- 背景: 「料理の例が圧縮の定義と逆向き」という指摘に対し、AI の修正案が記事の主題（人間の中に圧縮を残す）から外れ、語彙への外注側へ寄った。本人言「人間が情報の圧縮をできるようにする記事なのに、アウトソーシングだけになっていた」。指摘との整合だけを見ると、外れた案が正しく見える
- 変更案: 指摘を1件ずつ提示するステップに「修正案が記事の主題を強める向きか、それとも指摘の辻褄合わせに寄っているかを1行で添える」を足す。中心概念に触れる指摘では、修正案を2方向出して本人に選ばせる
- 期待される効果: レビューの反映が、整合性は上がるのに記事が薄くなる方向へ進むのを防げる

### 2026-07-28: blog-writing / blog-review - 圧縮を伴う推敲のあとは内容の再レビューを促す

- 対象: `.claude/skills/blog-writing/SKILL.md`（通し読みの締め）、`.claude/skills/blog-review/SKILL.md`（レビューの目的確認）
- 背景: critical-thinking-with-coding-agents を 14 章から 11 見出しへ圧縮した。直後に review を回すと、圧縮によって根拠の消えた箇所を3件見つけた。いずれも本人が OK を出した削除である。本人言「文章量が多かったのでとりあえず減らしたい感じで OK してた部分があった」「レビュー後のものもレビューし直すべき」。現行の blog-writing の締めには再レビューへの導線がない
- 変更案: blog-writing の締めに「章の統合や段落の削除を伴った回は、`/blog-review` を回して圧縮による情報の欠落を確認する」を足す。blog-review の目的確認では、選択肢に「圧縮で情報が落ちていないか」を明示的に並べる
- 期待される効果: 削りすぎの検知が運用に組み込まれる。今回は本人の指示で回したが、次回以降は手順として残る

### 2026-07-28: docs/writing-style.md - 禁則チェックをスクリプト化する

- 対象: `package.json`、`docs/writing-style.md`（禁則の表）、`.claude/skills/blog-writing/SKILL.md`（通し読みの準備）
- 背景: 2026-07-28 に禁則の節を作り、見出しの句読点・段落末の後置きの念押し・読点の引き伸ばし・太字・ダッシュ・「効く」の6項目を確認方法つきの表にまとめた。ただし確認は grep を1つずつ手で叩く形になっており、通し読みの準備でコマンドを6回打つことになる
- 変更案: 機械判定できる5項目（念押しを除く）を1つのスクリプトにまとめ、`pnpm kinsoku <file>` のような形で叩けるようにする。読点は3つ以上の文を一覧表示するだけにとどめ、列挙か対比かの判定は人が行う。表の「確認方法」列はスクリプト名に置き換え、正規表現はスクリプト側へ寄せる
- 期待される効果: 通し読みの準備が1コマンドで済み、確認漏れがなくなる。禁則を足すときもスクリプトの1行追加で運用に乗る

### 2026-07-27: blog-review / review-policy - 指摘に P0/P1 の優先度表記を導入する

- 対象: `.claude/skills/blog-review/SKILL.md`、`docs/review-policy.md`、`docs/templates.md`（review.md の表）
- 背景: critical-thinking-with-coding-agents の review で、3エージェントの指摘を統合した15件を1件ずつ提示した。全件反映・見送りゼロで消化できたが、本人言「1個ごとの方が集中できるけど、優先度もしくは重要度のようなものが欲しいかも。（P0やP1とかの表記でも良いかも）」。現行の review-policy は「読者の理解を妨げる／なくても困らないが直すとよい」の2段階で、統合後に順序の見通しが立ちにくかった
- 変更案: review-policy の2段階をそのまま P0（読者の理解を妨げる）／P1（なくても困らないが直すとよい）に対応づける。blog-review の統合ステップで、1件ずつ入る前に全件を優先度つきの一覧で提示する手順を足す。review.md の表の「重要度」列も P0/P1 表記に揃える
- 期待される効果: 消化の途中で「あと何件、どれが重いか」が分かり、時間が足りない回でも P1 を todo へ逃がす判断がしやすくなる

### 2026-07-27: blog-review - 指摘を「AI が書ける／本人に聞くしかない」で仕分ける

- 対象: `.claude/skills/blog-review/SKILL.md`
- 背景: critical-thinking-with-coding-agents の review での出来事。実例の追加と「言語化のやり方」の2件は AI が修正案を書けず、本人へ質問として返した。その結果、記事に無かった一次体験が引き出された。画像設定の過剰実装と、UI 語彙で指示すると速くなる話の2つである。本人言「聞かれて初めて思い出したケースと最近起きた事象だったので追加してなかったケースがある」
- 変更案: 統合ステップで各指摘に「AI が案を出せる／本人の一次体験が要る」の仕分けを付ける。後者は修正案を書かず質問として提示する、と進め方に明記する。draft を寝かせた記事では、寝かせている間に起きた出来事を明示的に聞く一手を足す
- 期待される効果: レビューが穴埋めだけでなく一次体験の引き出しとして機能する。AI が本人の体験を推測で書いてしまう事故も防げる
