# improvements

blog システム全体への改善提案ログ。対象はスキル（blog-\*）に限らない。

- スキル（`.claude/skills/**/SKILL.md`）
- ドキュメント（`docs/writing-policy.md` / `docs/structure.md` / `docs/templates.md` など）
- ワークフロー・命名規則・運用ルール
- **振り返りの仕組みそのもの**（retrospective / notes の構造）

「どのスキルを直すか」ではなく「次のセッションが楽になるよう、この blog システムのどこを変えるとよいか」を溜める場所。各提案は対象ファイルを明記する。
`/retrospective` が追記する。

**この一覧に載るのは未適用の提案だけ**。ステータスのフラグは持たない。ユーザーが採用と判断したらその場で対象ファイルを編集し、この項目を削除する。却下したときも項目を削除する。採否とその理由は commit メッセージに書き、経緯は git 履歴で辿る。

## 提案ログ

1 項目の書き方は [templates.md](./templates.md)「改善提案ログの項目」を参照。

### 2026-09-26: blog-writing の SKILL.md - 執筆モードで「引っかかり」をその場で聞く

- 対象: `.claude/skills/blog-writing/SKILL.md` の執筆モード 3.(e)
- 背景: business-productivity-cost-reduction で、事実の誤りが2件、通し読みまで残った。サーバーレスの恩恵と、プロビジョンドを勧める出どころで、どちらも本人が draft 時に少し引っかかっていた記述である。本人は「後で直せばよい」と思っていた
- 変更案: (e)「ユーザーの反応を待つ」に、「本文案の中で、書いていて少しでも引っかかる事実があれば、後回しにせずここで挙げてもらう」を添える
- 期待される効果: 事実のずれを draft の往復で拾え、通し読みの1件を流れやリズムの指摘に使える

### 2026-09-26: retrospective の Stop hook - 今のセッションで変更がないときは発火しない

- 対象: `.claude/hooks/retrospective-trigger.sh`
- 背景: 通し読みの準備メッセージの直後、このセッションではまだ works/ を変更していないのに hook が発火した。同じ日の前回セッションの変更に反応したとみられる（スクリプトは未確認で推測）。本人は「振り返りは後でいい」と答え、通し読みが終わってから実施した
- 変更案: 判定を「セッション開始時点からの works/・articles/ の差分」に絞る（例: セッション開始時の HEAD を記録し、それ以降のコミットか作業ツリーの変更があるときだけ促す）
- 期待される効果: 作業の冒頭で振り返りを促されて流れが止まるのを防ぐ

### 2026-09-26: blog-review の SKILL.md - 修正案の文面を禁則と textlint で先に確かめる

- 対象: `.claude/skills/blog-review/SKILL.md` の進め方 4.
- 背景: business-productivity-cost-reduction の review で、AI の修正案に禁則の「効く」が2回混入し、1件は本文に残った。合意した案が textlint（助詞の重複・読点4つ）で止まり、コミット時に言い回しを変えたことも4回あった。スキルは「文体を直さない」としているが、修正案として本文に入る文面は書いている
- 変更案: 4. に「修正案の文面は、提示する前に docs/writing-style.md の禁則表と textlint で確かめる」を1行足す
- 期待される効果: 合意した文面のまま反映でき、禁則の語が review 経由で本文へ入るのを防ぐ

### 2026-09-26: blog-review の SKILL.md - 起動方法の記述を今のツールに合わせる

- 対象: `.claude/skills/blog-review/SKILL.md` の進め方 2.
- 背景: SKILL.md は「3 つとも Foreground（`run_in_background: false`）で受け取る」としている。今の Agent ツールにこの引数はなく、3件ともバックグラウンドで動いた。結果は通知で1件ずつ届き、全件そろうまで待つ往復が増えた
- 変更案: 「Foreground で受け取る」を「3 件の完了通知がそろってから統合する。途中で届いた結果は提示しない」に書き換える
- 期待される効果: 手順と実際の挙動がずれず、途中経過の報告が減る

### 2026-09-26: blog-outline の SKILL.md - リード方針で書き手の立場と前提を決める

- 対象: `.claude/skills/blog-outline/SKILL.md` のリード方針の手順とテンプレート
- 背景: business-productivity-cost-reduction で、プラットフォームチームという立場と BtoB という前提が review まで本文になかった。本人言「忘れてた」「立場や前提を先に書いておく」
- 変更案: リード方針の確認に「書き手の立場（所属チームの役割・プロダクトの種類など）をリードで示すか」を1項目足し、outline.md のリード方針欄にも記入欄を置く
- 期待される効果: 読者が事例の重みを判断できる前提が、draft の最初から入る
