# improvements

blog システム全体への改善提案ログ。対象はスキル（blog-\*）に限らない。

- スキル（`.claude/skills/**/SKILL.md`）
- ドキュメント（`docs/writing-policy.md` / `docs/structure.md` / `docs/templates.md` など）
- ワークフロー・命名規則・運用ルール
- **振り返りの仕組みそのもの**（retrospective / notes の構造）

「どのスキルを直すか」ではなく「次のセッションが楽になるよう、この blog システムのどこを変えるとよいか」を溜める場所。各提案は対象ファイルを明記する。
`/retrospective` が追記する。

**この一覧に載るのは未適用の提案だけ**。ステータスのフラグは持たない。ユーザーが採用と判断したらその場で対象ファイルを編集し、この項目を削除する。却下したときも項目を削除する。採否とその理由は commit メッセージに書き、経緯は git 履歴で辿る。

## 提案ログ

1 項目の書き方は [templates.md](./templates.md)「改善提案ログの項目」を参照。

### 2026-09-26: blog-writing の SKILL.md - 執筆モードで「引っかかり」をその場で聞く

- 対象: `.claude/skills/blog-writing/SKILL.md` の執筆モード 3.(e)
- 背景: roi-thinking-for-engineers で、事実の誤りが2件、通し読みまで残った。サーバーレスの恩恵と、プロビジョンドを勧める出どころで、どちらも本人が draft 時に少し引っかかっていた記述である。本人は「後で直せばよい」と思っていた
- 変更案: (e)「ユーザーの反応を待つ」に、「本文案の中で、書いていて少しでも引っかかる事実があれば、後回しにせずここで挙げてもらう」を添える
- 期待される効果: 事実のずれを draft の往復で拾え、通し読みの1件を流れやリズムの指摘に使える

### 2026-09-26: retrospective の Stop hook - 今のセッションで変更がないときは発火しない

- 対象: `.claude/hooks/retrospective-trigger.sh`
- 背景: 通し読みの準備メッセージの直後、このセッションではまだ works/ を変更していないのに hook が発火した。同じ日の前回セッションの変更に反応したとみられる（スクリプトは未確認で推測）。本人は「振り返りは後でいい」と答え、通し読みが終わってから実施した
- 変更案: 判定を「セッション開始時点からの works/・articles/ の差分」に絞る（例: セッション開始時の HEAD を記録し、それ以降のコミットか作業ツリーの変更があるときだけ促す）
- 期待される効果: 作業の冒頭で振り返りを促されて流れが止まるのを防ぐ
