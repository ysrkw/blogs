# process-notes

ワークフロー（ideate → outline → draft → polish）を通して効いた進め方、詰まったパターンを蓄積する。

## 効いた進め方

- **H2 構造案を提示すると、それまで言葉にならなかった軸の違和感が表面化する**。抽象的に「方向性合っていますか？」と聞くより、具体的な構造を見せたほうが、本人の潜在的な方向性が言語化される。2026-05-26 organization-as-software では、H2 4 本案を見て「体験談中心ではなく思考フレーム中心にしたい」と転換した
- **セッション中に概念整理が言語化された瞬間、記事の射程が拡張されることもある**。整理が固まる前に出てこなかった応用・接続が、整理直後に湧く。2026-05-26 critical-thinking-with-coding-agents の例。論理／批判をループ構造として整理した直後に「このループはエージェントのエンジニアリングにも応用できる」が outline 終盤で出てきた。ideate のときには無かった
- **事前に技術勉強会で話した、または検索で下調べした題材は、ideate の最初の発言で完成度高く出てくる**。roi-thinking-for-engineers では初発言の時点で「費用対効果 vs 投資対効果」「2 軸」「PdM 視点」まで揃っていた。本人提案「事前にググっておくのは有効」。次回 ideate では冒頭で事前準備の有無を確認したい
- **セクションごとに区切って往復すると二重に効く**。本人言「セクションごと区切ることで、新たな発見があるのと人間側のレビュー負担が減りやすかった」。塊が小さいほどレビューしやすく、書いている途中で追加要素も湧く（2026-06-21 organization-as-software）
- **outline を寝かせてから draft に入ると射程が拡張される**。organization-as-software（outline 5/15 → draft 6/21）で土台（成長圧の新 H2）・比喩（細胞の新陳代謝）・トレードオフ（銀の弾丸はない）が追加された。critical-thinking-with-coding-agents（outline 5/26 → draft 6/23）でも再現。本人言「下書きで全文を見たから出てきた。時間が結構経って執筆しているのと別の記事の作成経験から、もっと補強すべきだと気付いた」。要因は3つ（全文を通して見た／時間経過／他記事の執筆経験で目が肥えた）。申し送り「アウトラインはあくまでスナップショットまたは過程なので、良いものが見つかればもっと記事を拡張すべき」
- **draft で湧いた補強候補は本文に即書かず todo.md へ逃がすと、ベース完成を止めない**。critical-thinking-with-coding-agents の draft で、全文完成後に補強角度（言語化／デザイン類似／良いものはシンプル／実装しない経験則）が連続で出た。本文に織り込むと発散するため `drafts/{slug}/todo.md` に候補を集約し、ベースを先に commit/push した。再開時はまず todo.md を読む（2026-06-23）
- **反映直後の本文が、次の連想の引き金になる**。2026-07-12 critical-thinking-with-coding-agents の draft 再開。todo 消化のはずが、新角度（探究心／LLM は増幅器／シンプルの2種類／知性補助の歴史）が会話中に連鎖した。本人言「実際に反映された記事を見て、記憶から掘り起こしてこれとも関連があるなとなって追加しました」。セクション合意→即反映→本文提示のサイクル自体が、記憶の索引として機能する
- **todo 項目の消化ごとに段階的コミットする**（2026-07-12 本人指示「項目が消化できたら、段階的にコミットしておいて欲しい」）。draft 中の常設運用。push は別途指示を待つ

## 図（Mermaid）作りの知見（2026-07-19）

critical-thinking-with-coding-agents で見出し「論理的思考は線路を敷く。批判的思考は分岐を切り替える」に図を追加した際の学び。

- **本文の文脈と関係ない図は作らない**（本人申し送り）。図がバイブコーディング対比まで膨らみ、「見出しの説明をしたいだけだった」と原点に戻した。図が本文から独立し始めたら、図を直すのではなく別セクションを増やすなど構成自体を見直す
- **図に起こすと説明の抜けが見える**。図化の途中で「レビューには論理と批判の2つの層がある」という本文の不足に気づき、段落を追加した。本人言「アイディアは広げるべきなので使える時は使う」
- **図のラベルの語彙は、比喩側か現実側かを最初に決める**。比喩の語（直進・徒歩）と開発の語（レビュー・実装）の間で 10 往復ほど揺れた。着地は「図は現実の開発の語、比喩は本文が担う」
- **消化済み todo は振り返り時に notes へ吸収して todo.md から削除する**（2026-07-19 本人指示）。判断の経緯は git 履歴に残る
  - 指示の原文「todo.md はある程度終わったので消せるようにしておいて欲しい」

## 観察された傾向

- **独自角度はその場で言語化されるパターンが多い**。roi-thinking-for-engineers では、独自角度が会話中に即興で出てきた。角度は「エンジニアリングを組織全体へ広げる課題に取り組んでいる立場」で、前作 critical-thinking-with-coding-agents との接続は後付け。シリーズ通底テーマを前提にせず、毎回その場で独自角度を引き出す質問設計が必要

## 詰まったパターン

- **書き手が頭の中で持っていた仮タイトル／仮方向を AI が聞き出していないと、タイトル案の往復が増える**。本人提案で着地するパターンになる（2026-05-26：3 案 → 改稿 3 案 → 副題なし 3 案 → 本人提案 で着地）
- **仮タイトルがあっても探索の往復には価値がある**。2026-05-26 critical-thinking-with-coding-agents の例。本人発言「もっと早く着地したかったが、会話することで思い出したこともあったので、そこまで無駄ではなかった」。ヒアリングして仮タイトルを起点にしつつも、探索をゼロにはしない設計が望ましい
- **修正を何度も重ねるセッションでは、AI が承認していない編集・挿入を出しやすい**。2026-06-23 organization-as-software の polish で、textlint 指摘を承認なしに連続適用してしまった。「なんか勝手に変更してない?」「L73 しか許可してないはず」で停止し、原状復帰した。本人言「claude code が勝手に出力してくるケースがあるので気をつける、修正を何度もすると発生するかも」。長い修正ループでは 1 操作ずつ承認を取り、差分を都度提示する

## 推敲（polish）の進め方

- **文を切るより、まず落とせる読点を削る**（本人申し送り）。一文の長さそのものより読点（`、`）の密度のほうが気になるポイント。文頭の呼吸の読点（「つまり、」「もちろん、」等）は残し、主語・話題の直後にある落とせる読点を削る（2026-06-21 organization-as-software polish：約 24 箇所）
- **humanizer は検出ツールとして使い、適用は 1 項目ずつ本人判断**。ダッシュ（§14）は全削除したが、宣伝臭・三点強調・アフォリズム等の一括書き換えは「一次体験・語りが削れる」ため不適用とした（2026-06-21）
- **「後で校正し直したい」ときは `articles/` へ移さず draft 据え置き**。`status: published` は「完成・公開可」の意味づけマーカーで、実際に外へ出るのは push のみ。再校正の余地を残すなら draft のままコミットで成果を保全する（2026-06-21）

## 機械校正（textlint）の運用知見（2026-06-22 導入）

運用原則は CLAUDE.md「AI の執筆姿勢」、効かせる経路と設定は docs/markdown.md を参照。ここでは導入時に得た固有の学びだけ残す。

- **テンプレの違反は生成物に伝播する**。blog-ideate のテンプレの `想定読了時間` が ja-technical-writing に引っかかり、過去の全 ideas に伝播していた（`読了時間の目安` に直して根を断った）。テンプレは各 SKILL.md 末尾のコードブロックに同梱されており textlint の自動対象外なので、新ルール導入時は手動で（または最初の生成物で）通す
- **textlint v15 は明示ファイル渡し・glob 展開のいずれでも `.textlintignore` を適用しない**（`notes/_x.md` を直接渡すと lint された）。除外はツール側で担保できないので、pre-commit は lefthook の glob で先に絞っている。`.textlintignore` は IDE 拡張や生 `textlint <file>` 実行時の保険として残る
- **lefthook の glob はトップ直下の flat ファイルを拾わない**。`{ideas,drafts,articles}/**/*.md` という設定は `ideas/{slug}.md`（ネストなし）を取りこぼす。末尾を `/**.md`（gobwas のスーパースター）に変えると flat と nested を両方カバーする（実測確認済み）
- **引用ブロック（`>`）と箇条書き（`-`）で textlint の効きが違う**。`>` は ja-technical-writing の prose ルールが効かず、`-` にすると効く。古い記事のスタイル統一で `>`→`-` に変えると、lint されていなかった生文（助詞連続・一文長）がまとめて顕在化する。`>` を lint 逃れに使わない（生メモでも校正する方針）
- **pre-commit の oxfmt は gitignored ファイルも検査する**。lefthook の `oxfmt --check` は staged 限定でなく全ファイルを対象にする。そのため gitignore 済みの `.claude/settings.local.json` の整形崩れでもコミットが止まる。中身を変えず `pnpm exec oxfmt <file>` で整形だけ直せば、他チェックを通したまま正規にコミットできる。--no-verify で全チェックを飛ばさない（2026-06-23）
- **no-doubled-joshi は複合語に含まれる助詞も数える**。たとえば『ように』の語中の助詞も対象。同じ助詞が一文に2回出ると違反するが、読点を挟めばリセットされる。max-ten は一文の読点4つで発火。draft 中は都度言い換えて通した（2026-06-23、この知見メモ自体も「に」2回で弾かれた）

## 出典・参照の選び方（2026-07-12）

critical-thinking-with-coding-agents の draft で、出典を選ぶ場面が3回あった（増幅器・分散学習・理解負債）。本人の選定基準は3つ。

- **アクセスすれば読めること**。本人言「ネットの記事はアクセスすれば読めること、出典元が一定の価値のあるウェブサイトであることにしたい」
- **出典元・著者に価値や実績があること**。Litt の講演録は「Notion の人も実績がある人だから引用に入れた」
- **AI の学習資料として話題に上がる場所という観点**。AI の学習資料によく上がるものを選ぶ観点もあるかもしれない、arXiv はまさにそれ、と本人が言語化（verbatim はセッションメモ参照）
- 実例: 増幅器の出典で DORA レポート（権威・知名度）より arXiv 論文を「読みやすいし」で選んだ。権威性より読者が読めるかを重視
- リンクの形式は「テキストの後にリンクだけの行」。括弧書きで本文の流れを切らない（2026-07-12 本人指定）
