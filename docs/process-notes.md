# process-notes

ワークフロー（ideate → outline → draft → review → publish）を通して効いた進め方、詰まったパターンを蓄積する。

## 効いた進め方

- **H2 構造案を提示すると、それまで言葉にならなかった軸の違和感が表面化する**。抽象的に「方向性合っていますか？」と聞くより、具体的な構造を見せたほうが、本人の潜在的な方向性が言語化される。2026-05-26 organization-as-software では、H2 4 本案を見て「体験談中心ではなく思考フレーム中心にしたい」と転換した
- **セッション中に概念整理が言語化された瞬間、記事の射程が拡張されることもある**。整理が固まる前に出てこなかった応用・接続が、整理直後に湧く。2026-05-26 critical-thinking-with-coding-agents の例。論理／批判をループ構造として整理した直後に「このループはエージェントのエンジニアリングにも応用できる」が outline 終盤で出てきた。ideate のときには無かった
- **事前に技術勉強会で話した、または検索で下調べした題材は、ideate の最初の発言で完成度高く出てくる**。business-productivity-cost-reduction では初発言の時点で「費用対効果 vs 投資対効果」「2 軸」「PdM 視点」まで揃っていた。本人提案「事前にググっておくのは有効」。次回 ideate では冒頭で事前準備の有無を確認したい
- **セクションごとに区切って往復すると二重に効く**。本人言「セクションごと区切ることで、新たな発見があるのと人間側のレビュー負担が減りやすかった」。塊が小さいほどレビューしやすく、書いている途中で追加要素も湧く（2026-06-21 organization-as-software）
- **outline を寝かせてから draft に入ると射程が拡張される**。organization-as-software（outline 5/15 → draft 6/21）で土台（成長圧の新 H2）・比喩（細胞の新陳代謝）・トレードオフ（銀の弾丸はない）が追加された。critical-thinking-with-coding-agents（outline 5/26 → draft 6/23）でも再現。本人言「下書きで全文を見たから出てきた。時間が結構経って執筆しているのと別の記事の作成経験から、もっと補強すべきだと気付いた」。要因は3つ（全文を通して見た／時間経過／他記事の執筆経験で目が肥えた）。申し送り「アウトラインはあくまでスナップショットまたは過程なので、良いものが見つかればもっと記事を拡張すべき」
- **draft で湧いた補強候補は本文に即書かず todo.md へ逃がすと、ベース完成を止めない**。critical-thinking-with-coding-agents の draft で、全文完成後に補強角度（言語化／デザイン類似／良いものはシンプル／実装しない経験則）が連続で出た。本文に織り込むと発散するため `drafts/{slug}/todo.md` に候補を集約し、ベースを先に commit/push した。再開時はまず todo.md を読む（2026-06-23）
- **反映直後の本文が、次の連想の引き金になる**。2026-07-12 critical-thinking-with-coding-agents の draft 再開。todo 消化のはずが、新角度（探究心／LLM は増幅器／シンプルの2種類／知性補助の歴史）が会話中に連鎖した。本人言「実際に反映された記事を見て、記憶から掘り起こしてこれとも関連があるなとなって追加しました」。セクション合意→即反映→本文提示のサイクル自体が、記憶の索引として機能する
  - 2026-09-26 business-productivity-cost-reduction でも再現した。営業サイドの事情、冗長化できなかった原因、Route 53、カスタマーサクセスチーム、リサーチの順序が、本文を見たあとに足された。記事を貫く軸（観察してから手を動かす）もこの経路で入った。本人言「もともと意識していたが、記事の生成を観察して、入れるべきだと感じた」
- **数字は記憶ではなく一次データで裏を取る**（2026-09-26 business-productivity-cost-reduction の draft）。CI の実行時間を `gh` で取得し、移行コミットの前後で比べた。Prettier→oxfmt は記憶の「1分から10秒台」に対し、実測は約50秒から約25秒だった。実測値で書いた。本人言「実測で書けたのは良かった、可能なら標準にしたい」。取得先の提案は本人から出た（「github cliで…のリポジトリのアクションを見に行けば、実態の確認はできるかも」）。同じ PR に入った別の変更（キャッシュ再利用、ワーカー数の指定）で数字が混ざらないよう、比べる期間を絞った
- **todo 項目の消化ごとに段階的コミットする**（2026-07-12 本人指示「項目が消化できたら、段階的にコミットしておいて欲しい」）。draft 中の常設運用。push は別途指示を待つ
- **寝かせた期間が長い idea は、outline の冒頭でその間の一次体験を聞くと構想ごと出てくる**（2026-09-26 business-productivity-cost-reduction）。idea から4か月あけた outline で、4件の体験が加わり、軸は3回動いた。本人言「4ヶ月の中でどう記事にするか考えて伝えました」。軸の移動は迷走ではなく、頭の中で固まっていた構想を順に出す過程だった。AI は各回でコンセプトを言い直して確認し、ideate には戻らなかった
- **矛盾を outline の段階で問うと、主張の前提が固まる**（2026-09-26）。webhook の移行は部品が増えるため、「シンプルに作る」と食い違って見えた。AI が「シンプル」の意味を2択で問い、本人の説明で「実態を測ってから育てる順序」に定まった。本人言「記事の矛盾や欠点は早期に見つけておきたい」

## 図（Mermaid）作りの知見（2026-07-19）

critical-thinking-with-coding-agents で見出し「論理的思考は線路を敷く。批判的思考は分岐を切り替える」に図を追加した際の学び。

- **本文の文脈と関係ない図は作らない**（本人申し送り）。図がバイブコーディング対比まで膨らみ、「見出しの説明をしたいだけだった」と原点に戻した。図が本文から独立し始めたら、図を直すのではなく別セクションを増やすなど構成自体を見直す
- **図に起こすと説明の抜けが見える**。図化の途中で「レビューには論理と批判の2つの層がある」という本文の不足に気づき、段落を追加した。本人言「アイディアは広げるべきなので使える時は使う」
- **図のラベルの語彙は、比喩側か現実側かを最初に決める**。比喩の語（直進・徒歩）と開発の語（レビュー・実装）の間で 10 往復ほど揺れた。着地は「図は現実の開発の語、比喩は本文が担う」
- **消化済み todo は振り返り時に notes へ吸収して todo.md から削除する**（2026-07-19 本人指示）。判断の経緯は git 履歴に残る
  - 指示の原文「todo.md はある程度終わったので消せるようにしておいて欲しい」

## 観察された傾向

- **独自角度はその場で言語化されるパターンが多い**。business-productivity-cost-reduction では、独自角度が会話中に即興で出てきた。角度は「エンジニアリングを組織全体へ広げる課題に取り組んでいる立場」で、前作 critical-thinking-with-coding-agents との接続は後付け。シリーズ通底テーマを前提にせず、毎回その場で独自角度を引き出す質問設計が必要

## 詰まったパターン

- **書き手が頭の中で持っていた仮タイトル／仮方向を AI が聞き出していないと、タイトル案の往復が増える**。本人提案で着地するパターンになる（2026-05-26：3 案 → 改稿 3 案 → 副題なし 3 案 → 本人提案 で着地）
- **仮タイトルがあっても探索の往復には価値がある**。2026-05-26 critical-thinking-with-coding-agents の例。本人発言「もっと早く着地したかったが、会話することで思い出したこともあったので、そこまで無駄ではなかった」。ヒアリングして仮タイトルを起点にしつつも、探索をゼロにはしない設計が望ましい
- **修正を何度も重ねるセッションでは、AI が承認していない編集・挿入を出しやすい**。2026-06-23 organization-as-software の polish で、textlint 指摘を承認なしに連続適用してしまった。「なんか勝手に変更してない?」「L73 しか許可してないはず」で停止し、原状復帰した。本人言「claude code が勝手に出力してくるケースがあるので気をつける、修正を何度もすると発生するかも」。長い修正ループでは 1 操作ずつ承認を取り、差分を都度提示する

## 推敲（review）の進め方

- **文を切るより、まず落とせる読点を削る**（本人申し送り）。一文の長さそのものより読点（`、`）の密度のほうが気になるポイント。文頭の呼吸の読点（「つまり、」「もちろん、」等）は残し、主語・話題の直後にある落とせる読点を削る（2026-06-21 organization-as-software polish：約 24 箇所）
- **humanizer は検出ツールとして使い、適用は 1 項目ずつ本人判断**。ダッシュ（§14）は全削除したが、宣伝臭・三点強調・アフォリズム等の一括書き換えは「一次体験・語りが削れる」ため不適用とした（2026-06-21）
- **レビューの穴には2種類ある。「聞かれて初めて思い出す」ものと「時間的に新しすぎてまだ書いていない」もの**（2026-07-27）。blog-review で AI が書けずに本人へ聞き返した指摘が2件あった。本人言「聞かれて初めて思い出したケースと最近起きた事象だったので追加してなかったケースがある」。後者は記事を寝かせている間に起きた出来事が反映されない構造的な穴で、「outline を寝かせると射程が拡張される」の裏返し。draft を寝かせた記事ほど、review で最近の一次体験を明示的に聞くとよい
- **観点を3エージェントに分割した並列レビューは、1件ずつ消化する形と相性が良い**（2026-07-27）。指摘15件を1件ずつ提示して全件反映、見送りゼロ。本人言「1個ごとの方が集中できるけど、優先度もしくは重要度のようなものが欲しいかも。（P0やP1とかの表記でも良いかも）」
- **圧縮を主題にした推敲では、削る動機が「量を減らしたい」に傾くと根拠まで落ちる**（2026-07-28）。critical-thinking-with-coding-agents で 14 章から 11 見出しへ圧縮した直後の review で、圧縮によって根拠の消えた箇所を3件見つけた。いずれも本人が OK を出した削除である。本人言「文章量が多かったのでとりあえず減らしたい感じで OK してた部分があった」。申し送りは本人言「レビュー後のものもレビューし直すべき」。削る前に、その文が装飾なのか根拠なのかを1回言語化する
- **章を減らす手は2つある。削除による圧縮と、H3 への格下げによる統合**（2026-07-28）。前回記事と H2 の数を比べると当たりがつく。organization-as-software は H2 8 個・H3 9 個で、H3 が並列の列挙を担って H2 を抑えていた。critical-thinking-with-coding-agents は同じ役割の内容を H2 として並べたため 14 個に膨らんだ
- **却下ゼロが続くのは指摘の質ではなく提示の粒度の効果**（2026-07-28）。2回のレビューで計 34 件、全件反映・却下ゼロだった。本人言「問題ない。1件ごとだから項目に集中できる」。判断の集中を作っているのは「1回1件」の原則である
- **lint 設定はリポジトリ全体に効く。作業メモの都合で緩めない**（2026-07-28）。review.md の日付ごとの小見出しが MD024（見出しの重複）に当たり、AI が `siblings_only` を設定に足して通した。本人が差し戻し、フォーマット側を直した。理由は本文の lint 基準が下がること（verbatim はセッションメモ参照）。作業用ドキュメントの構造をツールに合わせるほうが、記事の品質基準を守れる。代わりに採った形は、回ごとの節を `## YYYY-MM-DD` で積み、中の「良かった点」「指摘」「補足」を H3 でなくリード文でラベルする書き方（太字ラベルは MD036 に当たる）
- **レビュー指摘を機械的に潰すと、記事の主題から外れることがある**（2026-07-28）。「料理の例が圧縮の定義と逆向き」という指摘に対し、AI は「レシピという語彙が説明の手間を圧縮する」側へ寄せ直した。本人が「レシピが無くても作れるようになると脳に圧縮したといえることを記載した方が良い」と足した。本人言「人間が情報の圧縮をできるようにする記事なのに、アウトソーシングだけになっていた」。指摘の整合性だけを見ると、語彙への外注（アウトソーシング）側へ寄る修正が自然に見えるが、記事が扱いたいのは人間の中に圧縮が残る側だった。修正案は指摘との整合ではなく記事の主題との整合で選ぶ
- **同じ記事のレビューを重ねても、指摘は減りきらない**（2026-07-28）。3回目のレビュー（計45件目まで）でも高3件・低8件が出た。ただし3エージェントとも「公開を止めるレベルの欠陥はない」で判定が一致した。回を重ねるときは全件消化より、公開可否の判定を先に取ると区切りをつけやすい
- **「後で校正し直したい」ときは `articles/` へ移さず draft 据え置き**。`status: published` は「完成・公開可」の意味づけマーカーで、実際に外へ出るのは push のみ。再校正の余地を残すなら draft のままコミットで成果を保全する（2026-06-21）
- **draft で「後で直せばよい」と流した引っかかりは、通し読みで事実の訂正として出てくる**（2026-09-26 business-productivity-cost-reduction）。訂正は2件あった。サーバーレスの恩恵は「デプロイの自動化」ではなく「常駐インスタンスが不要になったこと」だった。DynamoDB でプロビジョンドを勧めていた出どころは、公式でなくコスト最適化の記事だった。本人はどちらも書いたときから少し引っかかっていたが、後で直せばよいと思っていた。AI が流れの指摘のために文脈から意味を推した案を出すと、それが呼び水になって訂正が出た。申し送りは本人言「引っかかったら後で直すと決めずその場で言う」
- **2案を出すと、本人は削っても違和感のないほうを選ぶ**（2026-09-26）。通し読みで A/B を出した5回のうち4回は、削るだけ・元の文を残すほうの A を選んだ。本人言「カットしても違和感がないから」。案を作るときは、まず削るだけで通るかを試し、それを A に置く
- **段落を移したり合流させたりした直後は、指示語と言葉の重なりが次の1件になる**（2026-09-26）。IT COMPASS の段落を移すと「そのうち」の指す先が遠くなり、「数字は説得力になる」を段落末へ移すと次の1文段落と「説得力」「提案」が重なった。移動を反映したら、前後の指示語と重複語をその場で読み直す
- **事例が完了したのか途中なのかは、review で改めて確かめる**（2026-09-26 business-productivity-cost-reduction）。webhook の移行はまだ本番前だったのに、本文は「移行し、費用を抑えました」と完了形で書かれていた。削減額を聞いた質問への答え「これから本番に出るので数字はまだ出せてない」で初めて分かった。本人言「AIが過去形で書いてしまったかも」。AI は事例を完了形に整えがちなので、成果を書いた文は時制を本人に確かめる
- **書き手の立場と前提は、本人の頭の中にあっても本文に落ちていないことがある**（2026-09-26）。「プラットフォームチーム（チームトポロジーの意味）としての実績をもとに書いた」「BtoB のプロダクト」という土台が、review までリードとまとめのどちらにもなかった。本人言「忘れてた」。ideate では立場が独自角度として語られていた（「観察された傾向」参照）が、本文へは移っていなかった。申し送りは本人言「立場や前提を先に書いておく」
- **数字が出せないときは、数字の代わりになる事実で主張をつなぐ**（2026-09-26）。金額は出せなかったが、「GitHub Actions の無料枠を毎月超えて課金されていた」「通常の利用の範囲でも赤字になる値段」という事実で、CI の短縮とマイクロサービスの廃止を費用の軸へつなげた。根拠の担当と読者への価値の担当が挙げた P0 は、どちらもこの形で閉じられた

## 機械校正（textlint）の運用知見（2026-06-22 導入）

運用原則は CLAUDE.md「AI の執筆姿勢」、効かせる経路と設定は docs/markdown.md を参照。ここでは導入時に得た固有の学びだけ残す。

- **テンプレの違反は生成物に伝播する**。blog-ideate のテンプレの `想定読了時間` が ja-technical-writing に引っかかり、過去の全 ideas に伝播していた（`読了時間の目安` に直して根を断った）。テンプレは各 SKILL.md 末尾のコードブロックに同梱されており textlint の自動対象外なので、新ルール導入時は手動で（または最初の生成物で）通す
- **lefthook の glob はトップ直下の flat ファイルを拾わない**。`{ideas,drafts,articles}/**/*.md` という設定は `ideas/{slug}.md`（ネストなし）を取りこぼす。末尾を `/**.md`（gobwas のスーパースター）に変えると flat と nested を両方カバーする（実測確認済み）
- **引用ブロック（`>`）と箇条書き（`-`）で textlint の効きが違う**。`>` は ja-technical-writing の prose ルールが効かず、`-` にすると効く。古い記事のスタイル統一で `>`→`-` に変えると、lint されていなかった生文（助詞連続・一文長）がまとめて顕在化する。`>` を lint 逃れに使わない（生メモでも校正する方針）
- **pre-commit の oxfmt は gitignored ファイルも検査する**。lefthook の `oxfmt --check` は staged 限定でなく全ファイルを対象にする。そのため gitignore 済みの `.claude/settings.local.json` の整形崩れでもコミットが止まる。中身を変えず `pnpm exec oxfmt <file>` で整形だけ直せば、他チェックを通したまま正規にコミットできる。--no-verify で全チェックを飛ばさない（2026-06-23）
- **no-doubled-joshi は複合語に含まれる助詞も数える**。たとえば『ように』の語中の助詞も対象。同じ助詞が一文に2回出ると違反するが、読点を挟めばリセットされる。max-ten は一文の読点4つで発火。draft 中は都度言い換えて通した（2026-06-23、この知見メモ自体も「に」2回で弾かれた）

## 出典・参照の選び方（2026-07-12）

critical-thinking-with-coding-agents の draft で、出典を選ぶ場面が3回あった（増幅器・分散学習・理解負債）。本人の選定基準は3つ。

- **アクセスすれば読めること**。本人言「ネットの記事はアクセスすれば読めること、出典元が一定の価値のあるウェブサイトであることにしたい」
- **出典元・著者に価値や実績があること**。Litt の講演録は「Notion の人も実績がある人だから引用に入れた」
- **AI の学習資料として話題に上がる場所という観点**。AI の学習資料によく上がるものを選ぶ観点もあるかもしれない、arXiv はまさにそれ、と本人が言語化（verbatim はセッションメモ参照）
- 実例: 増幅器の出典で DORA レポート（権威・知名度）より arXiv 論文を「読みやすいし」で選んだ。権威性より読者が読めるかを重視
- リンクの形式は「テキストの後にリンクだけの行」。括弧書きで本文の流れを切らない（2026-07-12 本人指定）
- **要旨を本文に書き下ろせば、出典の読みやすさの制約が緩む**（2026-07-27）。2026-07-12 に増幅器の出典を DORA でなく arXiv にしたのは、DORA が Web でそのまま読めずアクセス導線が悪かったため。今回 review で「論文が何を示したか本文に書かれていない＝根拠として機能していない」と指摘され、要旨を3文で本文に書き下ろした。その結果、読者が原典へ飛ぶ必要が下がり、信憑性の高い DORA へ差し替えられた。本人言「Web で読めないのでユーザーの読みやすさの導線を考えて arXiv にしていた」。判断基準（読者が読めるか）は変わっておらず、要旨の書き下ろしが導線の重みを下げた
- **リンクを置くだけの引用は、出典の導線の良さに依存する**。逆に要旨を書くなら、多少アクセスしにくくても信憑性で選べる（2026-07-27）
- **出典は、記事の中心語がその資料に実際に出てくるかまで確認する**（2026-09-26）。本人が最初に挙げた IT COMPASS の記事には「事業生産性」の語がなかった。本人は事業生産性と事業インパクトをまとめて調べていた時期があり、その資料だった。語の有無を伝えると Findy Tools の登壇レポートが出てきて、定義の出典と流れの補強に役割を分けられた
