## リード文の方向性

<!-- 読者の関心をつかむ最初の3〜4文で何を伝えるか -->

- コーディングエージェントで作るスピードが上がり、開発者への要求はこれからも増えていく
- ただ、機能を足すことがそのまま利益になるとは限らない。使われなければ要らない機能になり、複雑性が次の開発のコストを押し上げる
- そこで、開発の速さではなく事業の投資対効果を見る「事業生産性」という考え方を紹介する
- この記事では、実態を測り数値で待ったをかけて、組織のボトルネックを解く動き方を一次体験から書く
- 入口は AI による加速というポジティブな話題にし、「要らない機能」のようなネガティブな話は2文目に回す

## 構成

### H2: 開発生産性から事業生産性へ

- 要点: 開発の速さではなく、事業の投資対効果で生産性を見る
- 含める要素:
  - Findy Tools の記事の定義。事業全体の投資対効果に焦点を当て、ROIC（投下資本に対する利益率）の向上を目標にする。開発組織の活動を「売上増加」「費用削減」「資本最適化」のどれに貢献するかで評価する
  - idea 段階の2軸（利益の最大化／コストの最適化）が「売上増加」「費用削減」に対応すること
  - 費用対効果と投資対効果の違い
  - lanitech の記事で「開発生産性を事業インパクトと結びつける流れ」を補強し、今後適応すべきと伝える
  - 「事業生産性」はまだ一部で言われ始めた言葉なので、本文で定義してから使う
  - エンジニアの人件費もコストに含まれることは釘を刺す程度にとどめる
- 一次体験・具体例: 特になし（用語の整理が中心）

### H2: 足した機能が次の開発を重くする

- 要点: 機能を足しても利益になるとは限らず、使われない機能や個別顧客向けの機能が複雑性を上げる
- 含める要素:
  - 使われなければ要らない機能になりうる
  - BtoB では個別の顧客向けの機能が増えがちで、システム全体の複雑性を上げる
  - 複雑性が次の開発のコストを跳ね上げる
- 一次体験・具体例: 引き継ぎクーポンシステム
  - 他社から引き継ぎ、誰も内情がわからない状態で EC2 で稼働していた
  - 1 年に数回しか使われず、止めることもできず運用費だけが発生し続けた
  - 急に利用が増えて障害が起き、開発サイドで気付けず経緯報告書が必要になった
  - それを契機に見直し、廃止した
  - 請求はトータルで見るとマイナスとしか思えない金額だった。2軸の両方が壊れ、障害対応のコストまで乗った事例

### H2: シンプルに作り実態を測ってから育てる

- 要点: 最初から複雑なしくみで本番に出さない。まずシンプルに実現し、ログや計測で実態を見てから最適化する
- 含める要素:
  - 「シンプル」は部品の数ではなく順序の話。実態を見てから育てる
  - 要求と実態と AWS のベストプラクティスを突き合わせて判断する
- 一次体験・具体例:
  - webhook: 最初は EC2 でシンプルに提供していた。ログを見ると、24 時間稼働し続ける EC2 ではデメリットになるアクセス量だった。API Gateway + Lambda + SQS + Lambda（後続処理）へ移行して費用を浮かせた。SQS はリクエストを早く捌きつつ、後続処理の失敗で遅延させないための仕組み。serverless を使ったのでデプロイの自動化も容易だった
  - DynamoDB: 利用実態を計測し、プロビジョンドよりオンデマンドの方が安いと分かって移行した。AWS のインフラ費用を下げた。削減の幅は draft で数値を確認する

### H2: 個人より組織のボトルネックを解く

- 要点: エージェントで個人だけが効率的になっても、開発体制の見直しが進む時代では勝てない。チームや部署の単位で恩恵が出るものを見つける審美眼が要る
- 含める要素:
  - 個人のボトルネックより組織のボトルネックの解消を優先する
  - 全体最適化をエンジニアリングしていこう、という記事の主張をここで言い切る
  - どの一次体験も、チームや部署の単位で恩恵を受ける改善だったという共通点
- 一次体験・具体例:
  - webpack v4 から v5 への移行で、遅かった開発環境のビルド時間を短縮した
  - プロダクト開発のリポジトリで、フォーマットツールを prettier から oxfmt に移行し、フォーマット検知の GitHub Actions の実行時間を削減した。ソースコードの規模が大きく、Rust 製ツールへの置き換えは将来の開発コストを下げる

### H2: 数字で待ったをかける

- 要点: AI で要求が増えるほど、そのまま作ってよいか、生産性を落とさないかを実態から調べ、数値で納得させて待ったをかけられる人が要る（防衛・セーフティネット）
- 含める要素:
  - 機能の最適化や廃止をエンジニアが説得力を持って提案できないと、AI による加速度的な開発に耐えられない
  - 時間がなくてあまり行われてこなかった探索業務（ディスカバリー）を、エンジニアも手伝う。語彙は organization-as-software で導入済みのものを再利用する
- 一次体験・具体例: クーポンシステムの見直しを、提案する側の視点から軽く振り返るか検討（重複に感じたら 2 つめの H2 だけにする）

## まとめで伝えたいこと

- 事業生産性をエンジニアリングするとは、全体最適を仕組みで回すこと
- 個人の心がけではなく、「作る前に測る」「作った後も測る」をプロセスに組み込む
