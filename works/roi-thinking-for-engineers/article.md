# 事業生産性をエンジニアリングする

コーディングエージェントのおかげで、機能を作るスピードは大きく上がりました。作れる量が増えたぶん、開発者に届く要求も増えています。ただ、機能を足すことがそのまま利益になるとは限りません。使われなければ要らない機能になり、増えた複雑性が次の開発のコストを押し上げます。

そこでこの記事では、開発の速さではなく事業の投資対効果で生産性を見る「事業生産性」という考え方を紹介します。そのうえで、実態を測って数値で待ったをかけ、組織のボトルネックを解いていく動き方を私の一次体験から書いていきます。

## 開発生産性から事業生産性へ

エンジニアが生産性と言うとき、多くは開発生産性を指します。よく使われる指標として DORA の Four Keys があります。デプロイの頻度、変更のリードタイム、変更失敗率、障害からの復旧時間の4つで、どれだけ速く安定して届けられるかを測ります。コーディングエージェントの浸透で、この数値は上げやすくなってきました。

速く届けた機能でも、使われなければ利益は増えません。Four Keys が良くなっても事業の成長につながるとは限らず、明後日の方向に開発陣営が向かってしまうことも多いです。

事業生産性は、その視点を事業の側へ広げたものです。開発生産性 Conference 2025 の登壇レポートでは、事業全体の投資対効果に焦点を当て、ROIC（投下資本に対する利益率）を上げることを目標にしています。開発組織の活動も「売上増加」「費用削減」「資本最適化」のどれに貢献したかで評価します。

[「開発生産性」ではなく、事業の投資対効果に向き合う「事業生産性」へ - Findy Tools](https://findy-tools.io/articles/onecareer-dev-productivity-con-2025/115)

この記事では、そのうち売上増加と費用削減の2つを扱います。

投資対効果は、費用対効果と混同されやすい言葉です。

- 費用対効果: かけた費用に見合う効果が出たかを見る。効果は作業時間の短縮や利用者の満足のように、お金以外で測ることもある
- 投資対効果: 投じたお金に対して、どれだけ利益が戻ってきたかを見る

機能を作る判断は費用対効果で語られがちです。事業生産性では、利益として戻ってくるかまで見ます。ここで言う費用には、開発するエンジニアの人件費も含まれます。

開発生産性を事業インパクトと結びつける流れは、ほかにも広がっています。

[開発チームの生産性を「事業インパクト」と結びつける新しい視点 - IT COMPASS](https://itcompass.lanitech.jp/blog/developer-productivity-business-impact/)

## 足した機能が次の開発を重くする

プロダクト開発はリリースしてからが本番と言われます。リリースした機能は、使われ方を見て育てていく対象になります。動かし続けるコストも、リリースしたその日から発生し始めます。使われている機能なら、そのコストは売上で回収できます。使われなければ、コストだけがかかり続けて開発の足枷になります。

BtoB のプロダクトでは、特定の顧客のために作った機能が増えがちです。個別の要望へ応えるたびに分岐や設定が増え、システム全体が複雑になります。複雑になったシステムでは、次の機能を足すときに確かめる範囲が広がり、開発のコストが跳ね上がります。

私の経験でこれがはっきり表れたのは、開発サイドとしてはあまり使ってほしくない、とあるマイクロサービスでした。5年ほど前に他社から引き継いだシステムで、中の仕組みを知っている人は誰もいません。単独の EC2 で独立したシステムとして動き続けていましたが、使われるのは1年に数回だけでした。止めてよいかも判断できず、運用費だけがかかり続けていました。

あるとき、そのシステムが急にやたらと使われるようになり、障害が起きました。複数のサーバーで冗長化できる作りになっておらず、アプリケーションのコードも一部の状態をサーバーのローカルで持っていました。1台で受けきれる限界を、増えたアクセスが超えてしまったのです。開発サイドでは気付けず、影響もあって経緯報告書を書くことになりました。これをきっかけに、システムを見直すことになりました。

見直してわかったのは、請求できていた金額の少なさです。開発サイドの意図もシステムの事情も営業サイドには伝わっておらず、売上を伸ばそうと機能を使う顧客から追加費用を取ってきてくれていました。ただ、AWS の運用費や関わる人件費を計算に入れると、まったく釣り合わない額でした。売上増加と費用削減のどちらにもつながっておらず、そこに障害対応のコストまで乗っていました。

見直しの結果、オプションとして提案していたそのマイクロサービスを外しました。代わりに別の SaaS ツールと連携して、代用できる手段を残しています。需要が少ないうちは自社で持たず、需要が増えたら運用費用の増えない形で作り直すほうが良いと判断しました。

## シンプルに作り実態を測ってから育てる

最初から複雑なしくみで本番に出す必要はありません。まずシンプルに実現して、ログや計測で実態を見てから最適化します。ここで言うシンプルは、部品の数が少ないことではありません。実態を見て方向を見定め、小さく一歩進み、その結果から学ぶという順序のことです。

コーディングエージェントは過剰な提案をしがちで、最初から壮大なアプローチを出してくることも多いです。それを抑えるために、シンプルとは何かを一度考えておくと役に立ちます。考えるときの参考には『シンプリシティ』がおすすめです。

[シンプリシティ―持続可能かつ人間的で効果的なソフトウェア開発 - O'Reilly Japan](https://www.oreilly.co.jp/books/9784814401710/)

webhook の受け口がその例です。SNS からの webhook を受け取るサーバーで、最初は EC2 でシンプルに提供していました。SNS からの通知なので、常にアクセスがあるとは限りません。ログを見ると、24時間動かし続けるほどではないアクセス量でした。そこで API Gateway と Lambda で受け、SQS を挟んで後続処理の Lambda へ渡す形に移行し、費用を抑えました。

SQS を挟んだ理由は2つあります。1つは、webhook の受理と、プロダクトで行いたい実際の処理を分けるためです。受理だけを先に済ませてリクエストを早く返せるので、後続処理が失敗しても受け口は遅れません。もう1つは、後続処理を共通にするためです。バッチ処理などでも同じ処理をしたいケースがあり、SQS に送れば別のプロセスからも共通の処理に任せられます。

サーバーレスの構成にしたことで、デプロイの自動化も簡単になりました。webhook の受け口は、Route 53 でドメインを解決しています。今回は別のサブドメインで移行したため SNS 側の送信先も切り替えましたが、次からは同じドメインのまま、エンドポイントの切り替えだけで内部の構成を入れ替えられます。

DynamoDB でも同じ順序で進めました。DynamoDB には、読み書きの容量を先に確保しておくプロビジョンドと、使った分だけ払うオンデマンドの2つの課金方式があります。プロビジョンドを勧める記事は多いものの、それは高い頻度でアクセスが続くケースの話です。私たちの用途は、定期的にデータを取得して蓄積する仕組みでした。プロビジョンドで動かしていると、突発的なリクエストに耐えられず失敗することもありました。

利用実態を計測すると、オンデマンドのほうが安く済むこともわかりました。オンデマンドへ移行すると、少なくとも月額200ドルのインフラ費用が浮きました。突発的なリクエストで失敗することもなくなり、一石二鳥の対応になりました。

プロビジョンドは、私が入社する前から使われていた方式です。課金方式の違いと利用実態を突き合わせずに決めた判断は、後から負債になることがあります。移行するときも、要求と実態と AWS のベストプラクティスを照らし合わせて、慎重に進めたいです。

## 個人より組織のボトルネックを解く

コーディングエージェントのおかげで、個人の作業は目に見えて速くなりました。個人だけが効率的になっても、開発体制そのものの見直しが進む時代には勝てません。優先したいのは、チームや部署の単位で恩恵が出るボトルネックの解消です。それを見つけるには、どこを直せば全体が速くなるかを見分ける審美眼が要ります。

私が最初にするのは、組織が何をボトルネックに感じているかの確認です。開発チームへリサーチすると、「開発環境の立ち上がりが遅い」「lefthook（Git のフックを管理するツール）での検証に時間がかかる」「テストが遅い」といった声が上がりました。私自身も開発していて、CI の遅さは気になっていました。手を動かすのはその後です。どこを直すかは憶測で決めず、自分の実感とチームの声、実測の数字を照らし合わせて決めています。一歩進む前に方向を見定めるという点で、これもシンプルな動き方です。TypeScript のバージョンアップや lint 系ツールのアップグレードも、同じ進め方で対応してきました。ここではそのうち3つを紹介します。

1つめは、webpack の v4 から v5 への移行です。開発環境の立ち上がりが遅いという声に応えたものです。CI の本番ビルドのテストでは、約90秒かかっていたビルドが約60秒になりました。開発環境のビルドも速くなり、同じリポジトリで開発する全員がその恩恵を受けました。

2つめは、フォーマットツールの Prettier から Rust 製の oxfmt への移行です。lefthook での検証に時間がかかるという声がきっかけでした。ソースコードの規模が大きく、CI でフォーマットを検知するステップは約50秒から約25秒と半分ほどになりました。コードが増えるほど実行時間も延びるので、速いツールへの置き換えは将来の開発コストも下げます。

3つめは、Jest の最新版への更新です。テストが遅いという声から対応しました。Jest 30 へ上げると同時に設定も整理し、CI でテストのキャッシュを再利用するようにしました。CI のユニットテストは、約3分かかっていたのが30秒以内で終わるようになりました。

紹介した3つは、私1人の作業を速くするためだけの改善ではありません。ビルド、フォーマットの検証、テストは、どれもチームの全員が毎日通る場所です。1回の待ち時間は数十秒から数分でも、人数と回数を掛ければ、組織全体で浮く時間は大きくなります。

全体最適は、開発チームの中だけの話ではありません。カスタマーサクセスチームでは、自社の顧客の利用実態や契約状態を調べるのに困っているケースが多くありました。そこで外部の SaaS ツールと契約し、データベースとの連携などをエンジニア側で手伝っています。効果が見えてくるのはこれからです。データベースの接続のように、エンジニアが協力しなければ前に進めないことを手伝うのも、組織の改善として大事な動きです。

個人の速さはエージェントが引き上げてくれるので、エンジニアが手を動かす先は全体の最適化です。

## 数字で待ったをかける

コーディングエージェントで作る速さが上がるほど、要求も次々に届きます。そのまま作ってよいのか、作ったあとに生産性を落とさないかを、実態から調べる人が要ります。数字で納得してもらい、必要なら待ったをかける。組織にとってのセーフティネットです。

運用費と請求額を並べた数字は、廃止を提案するときの説得力になります。とはいえ、リリースする前にどれくらいの費用がかかるかは、実際に動かしてみないと予測できないことも多いです。市場のプレッシャーから、そこを度外視してリリースすることもプロダクト開発ではよくあります。大事なのは、出した後の振り返りとフィードバックをおろそかにしないことです。PDCA の A（改善）を無視すれば、人はリリースして満足してしまいます。見るべきは、出したものが事業に貢献しているかどうかです。

機能の最適化や廃止をエンジニアが説得力を持って提案できなければ、AI による加速度的な開発に組織が耐えられません。

時間がなくて、これまであまり行われてこなかった仕事もあります。ディスカバリー（何を作るかを探る）です。エージェントのおかげで、デリバリー（実際に作る）にかかる時間は減りました。浮いた時間で、エンジニアもディスカバリーを手伝えます。先に書いた開発チームへのリサーチや、カスタマーサクセスチームの困りごとを聞いたことも、その1つです。

## まとめ

コーディングエージェントで作る速さが上がった今、見るべきは開発の速さだけではありません。足した機能が事業に貢献しているか、組織のどこにボトルネックがあるかを、実態と数字で確かめる必要があります。先に手を動かしてしまうのは、出戻りのコストが高い行為です。この記事の事例は、どれも観察して実態を調べ、実績から学んでから手を動かしてきました。『シンプリシティ』の「方向を見定め、一歩進み、学ぶ（Orient, Step, Learn）」は、この進め方と重なります。違和感のあるところから方向を見定め、シンプルな一歩を踏み出し、その結果を振り返って学ぶサイクルです。個人の改善に限らず、組織の改善にも当てはめていきたい考え方です。

事業生産性をエンジニアリングするとは、全体最適を仕組みで回すことだと考えています。個人の心がけに頼らず、作る前に測り、作った後も測ることをプロセスに組み込む。次に機能を足すとき、その機能が事業にどう返ってくるかを数字で語れるでしょうか。
