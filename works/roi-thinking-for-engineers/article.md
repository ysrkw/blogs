# 事業生産性をエンジニアリングする

コーディングエージェントのおかげで、機能を作るスピードは大きく上がりました。作れる量が増えたぶん、開発者に届く要求も増えています。機能を足すことが、そのまま利益になるとは限りません。使われなければ要らない機能になり、増えた複雑性が次の開発のコストを押し上げます。

この記事では、開発の速さではなく事業の投資対効果で生産性を見る「事業生産性」という考え方を紹介します。そのうえで、実態を測って数値で待ったをかけ、組織のボトルネックを解いていく動き方を書いていきます。題材は、BtoB のプロダクトを開発する組織のプラットフォームチームでの、私の一次体験です。プラットフォームチームは『チームトポロジー』の用語で、ほかのチームが使う基盤を提供するチームです。

## 開発生産性から事業生産性へ

エンジニアが生産性と言うとき、多くは開発生産性を指します。よく使われる指標として DORA の Four Keys があります（現在の DORA はデプロイ再作業率を加えた5つで測っています）。デプロイの頻度、変更のリードタイム、変更失敗率、障害からの復旧時間の4つで、どれだけ速く安定して届けられるかを測ります。コーディングエージェントの浸透で、デプロイの頻度やリードタイムといった速さの数値は上げやすくなってきました。2025年の DORA のレポートでは、AI の導入が安定性の低下と結びついていることも報告されています。

[DORA's software delivery performance metrics - DORA](https://dora.dev/guides/dora-metrics-four-keys/)

[Announcing the 2025 DORA Report - Google Cloud Blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)

速く届けた機能でも、使われなければ利益は増えません。Four Keys が良くなっても、事業の成長につながるとは限りません。開発チームが明後日の方向へ速く進んでしまうこともあります。

事業生産性は、生産性を見る視点を事業の側へ広げたものです。開発生産性 Conference 2025 の登壇レポートでは、事業全体の投資対効果に焦点を当て、ROIC（投下資本に対する利益率）を上げることを目標にしています。開発組織の活動も「売上増加」「費用削減」「資本最適化」のどれに貢献したかで評価します。

[「開発生産性」ではなく、事業の投資対効果に向き合う「事業生産性」へ - Findy Tools](https://findy-tools.io/articles/onecareer-dev-productivity-con-2025/115)

開発生産性を事業インパクトと結びつける流れは、ほかにも広がっています。

[開発チームの生産性を「事業インパクト」と結びつける新しい視点 - IT COMPASS](https://itcompass.lanitech.jp/blog/developer-productivity-business-impact/)

この記事では、事業生産性の3つの観点のうち、エンジニアが関わりやすい費用削減の面から考えます。

投資対効果は、費用対効果と混同されやすい言葉です。

- 費用対効果: かけた費用に見合う効果が出たかを見る。効果は作業時間の短縮や利用者の満足のように、お金以外で測ることもある
- 投資対効果: 投じたお金に対して、どれだけ利益が戻ってきたかを見る

機能を作る判断は費用対効果で語られがちです。事業生産性では、利益として戻ってくるかまで見ます。ここで言う費用には、開発するエンジニアの人件費も含まれます。

## 使われない機能がコストを生み続ける

プロダクト開発はリリースしてからが本番と言われます。リリースした機能は、使われ方を見て育てていく対象になります。動かし続けるコストも、リリースしたその日から発生し始めます。使われている機能でも、そのコストを売上で回収できているかは、運用費と請求額を並べてみるまでわかりません。使われなければ、コストだけがかかり続けて開発の足枷になります。

BtoB のプロダクトでは、特定の顧客のために作った機能が増えがちです。個別の要望へ応えるたびに分岐や設定が増え、システム全体が複雑になります。複雑になったシステムでは、次の機能を足すときに確かめる範囲が広がり、開発のコストが上がっていきます。

私の経験で使われない機能のコストがはっきり表れたのは、開発サイドとしてはあまり使ってほしくない、とあるマイクロサービスでした。5年ほど前に他社から引き継いだシステムで、中の仕組みを知っている人は誰もいません。単独の EC2 で独立したシステムとして動き続けていましたが、使われるのは1年に数回だけでした。止めてよいかも判断できず、運用費だけがかかり続けていました。

年に数回の利用のタイミングで、特定の顧客がまとめて使ったためにアクセスが例年よりずっと多くなり、障害が起きました。複数のサーバーで冗長化できる作りになっておらず、アプリケーションのコードも一部の状態をサーバーのローカルで持っていました。1台で受けきれる限界を、増えたアクセスが超えてしまったのです。開発サイドでは後手で気付く形になってしまい、経緯報告書を書くことになりました。

調査してわかったのは、有料のオプションとして請求できていた金額の少なさです。開発サイドの意図もシステムの事情も営業サイドには伝わっておらず、売上を伸ばそうと機能を使う顧客から追加費用を取ってきてくれていました。AWS の運用費や関わる人件費を計算に入れると、通常の利用の範囲でも赤字になる値段でした。売上増加と費用削減のどちらにもつながっておらず、そこに障害対応のコストまで乗っていました。

調査でわかった運用費と請求額の差をもとに、定例で各マネージャーへ今後の方針を提案し、合意をもらいました。そのオプションは外して EC2 も止め、運用費をなくしました。代わりに別の SaaS ツールと連携して、代用できる手段を残しています。値上げをすると、受注につながらない恐れがありました。中の仕組みを知る人がいないので、作り直すにはサービスを維持する要件をリバースエンジニアリングで洗い出すところから始めます。コーディングエージェントを使っても時間がかかり、直近に契約した顧客をその間待たせることになります。需要が少ないうちは自社で持たず、需要が増えたら運用費用の増えない形で作り直すほうが良いと判断しました。

## シンプルに作り実態を測ってから育てる

最初から複雑なしくみで本番に出す必要はありません。まずシンプルに実現して、ログや計測で実態を見てから最適化します。ここで言うシンプルは、部品の数が少ないことではありません。ユースケースに沿って、必要な処理だけで済む形にすることです。そこへたどり着くために、実態を見て方向を見定め、小さく一歩進み、その結果から学ぶという順序を踏みます。

コーディングエージェントは過剰な提案をしがちで、最初から壮大なアプローチを出してくることも多いです。それを抑えるために、シンプルとは何かを一度考えておくと役に立ちます。

webhook の受け口は、この順序で見直した例です。外部サービスからの webhook を受け取るサーバーで、もとは EC2 で動いていました。ログを見ると、24時間動かし続けるほどではないアクセス量でした。そこで API Gateway と Lambda で受け、SQS を挟んで後続処理の Lambda へ渡す形に移行を進めています。今のアクセス量なら、EC2 を動かし続けるより安く済む見込みです。

SQS を挟んだ理由は2つあります。1つは、webhook の受理と、プロダクトで行いたい実際の処理を分けるためです。受理だけを先に済ませてリクエストを早く返せるので、後続処理が失敗しても受け口は遅れません。もう1つは、後続処理を共通にするためです。バッチ処理などでも同じ処理をしたいケースがあり、SQS に送れば別のプロセスからも共通の処理に任せられます。

サーバーレスの構成にすれば、常駐するインスタンスを持つ必要がなくなり、OS の更新作業などから手が離れます。受け口のドメインは Route 53 で解決しているので、次からは同じドメインのまま、エンドポイントの切り替えだけで内部の構成を入れ替えられます。今回は別のサブドメインで移行するため、外部サービス側の送信先も切り替えます。

DynamoDB でも同じ順序で進めました。DynamoDB には、読み書きの容量を先に確保しておくプロビジョンドと、使った分だけ払うオンデマンドの2つの課金方式があります。DynamoDB のコスト最適化を調べると、プロビジョンドへの切り替えを勧める話がよく出てきます。プロビジョンドが向くのは、アクセスが安定していて、必要な容量を予測できる場合です。利用実態が見えていない段階で先に入れるものではありません。AWS の公式ドキュメントでも、多くの用途ではオンデマンドを既定として推奨しています。私たちの用途は、定期的なバッチ処理でデータを取得して蓄積する仕組みで、一気にアクセスの来る使い方が中心でした。プロビジョンドの条件には合わず、確保した容量を超えたリクエストが失敗することもありました。

[DynamoDB throughput capacity - Amazon DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/capacity-mode.html)

利用実態を計測すると、オンデマンドのほうが安く済むこともわかりました。オンデマンドへ移行すると、少なくとも月額200ドルのインフラ費用が浮きました。突発的なリクエストで失敗することもなくなり、一石二鳥の対応になりました。

プロビジョンドは、私が入社する前から使われていた方式です。課金方式は、決めたあとも今の状態が最適なのかを利用実態と照らして振り返らないと、後から負債になることがあります。移行するときも、計測した利用実態を要求と AWS のベストプラクティスに照らしてから切り替えています。

## 個人より組織のボトルネックを解く

コーディングエージェントのおかげで、個人の作業は目に見えて速くなりました。個人だけが効率的になっても、開発体制そのものを見直して速度を上げている競合他社には追いつけないと考えています。優先したいのは、チームや部署の単位で恩恵が出るボトルネックの解消です。それを見つけるには、どこを直せば全体が速くなるかを見分ける審美眼が要ります。

私が最初にするのは、組織が何をボトルネックに感じているかの確認です。プロダクトチームへリサーチすると、「開発環境の立ち上がりが遅い」「lefthook（Git のフックを管理するツール）での検証に時間がかかる」「テストが遅い」といった声が上がりました。私自身も開発していて、CI の遅さは気になっていました。どこを直すかは憶測で決めず、自分の実感とチームの声、実測の数字を照らし合わせてから手を動かします。一歩進む前に方向を見定めるという点で、これもシンプルな動き方です。

TypeScript のバージョンアップや lint 系ツールのアップグレードも、同じ進め方で対応してきました。ここでは、声の上がった3つを紹介します。

1つめは、webpack の v4 から v5 への移行です。開発環境の立ち上がりが遅いという声に応えたものです。約2分かかっていた開発環境の起動が約1分と、半分ほどになりました。CI で本番用のビルドを確かめるステップでも、約90秒かかっていたビルドが約60秒になり、同じリポジトリで開発する全員がその恩恵を受けました。

2つめは、フォーマットツールの Prettier から Rust 製の oxfmt への移行です。lefthook での検証に時間がかかるという声がきっかけでした。CI でフォーマットの崩れを検知するステップは、ソースコードの規模が大きいぶん約50秒かかっていました。oxfmt に替えると約25秒と、半分ほどになりました。コードが増えるほど実行時間も延びるので、速いツールへの置き換えは将来の開発コストも下げます。

3つめは、Jest の最新版への更新です。テストが遅いという声から対応しました。Jest 30 へ上げると同時に設定も整理し、CI でテストのキャッシュを再利用するようにしました。CI のユニットテストは、約3分かかっていたのが30秒以内で終わるようになりました。短縮の主な要因は、キャッシュの再利用でした。

紹介した3つは、私1人の作業を速くするためだけの改善ではありません。ビルド、フォーマットの検証、テストは、どれもチームの全員が毎日通る場所です。『HIGH OUTPUT MANAGEMENT』でいう、レバレッジの高い活動にあたります。1回の待ち時間は数十秒から数分でも、人数と回数を掛ければ、組織全体で浮く時間は大きくなります。CI の実行時間は費用にも直結します。GitHub Actions の無料枠を毎月超えて課金されていたので、実行時間を縮めることでその超過分も減らしたいと考えていました。

全体最適は、開発チームの中だけの話ではありません。カスタマーサクセスチームでは、自社の顧客の利用実態や契約状態を調べるのに困っているケースが多くありました。データベースの接続のように、エンジニアが協力しなければ前に進めない困りごとです。そこでカスタマーサクセスチームは、自社で一から BI を用意するのを待たずに済むよう、BI ツールのような外部の SaaS を自分たちで検討して導入しました。エンジニア側では、データベースとの連携などを手伝っています。効果が見えてくるのはこれからで、カスタマーサクセスチームの目標の達成度が上がるかで判断します。

個人の速さはエージェントが引き上げてくれるので、エンジニアが手を動かす先は全体の最適化です。

## 数字で待ったをかける

コーディングエージェントで作る速さが上がるほど、要求も次々に届きます。そのまま作ってよいのか、作ったあとに生産性を落とさないかを、実態から調べる人が要ります。数字で納得してもらい、必要なら待ったをかける役割は、組織にとってのセーフティネットになります。

リリースする前にどれくらいの費用がかかるかは、実際に動かしてみないと予測できないことも多いです。市場のプレッシャーから、そこを度外視してリリースすることもプロダクト開発ではよくあります。大事なのは、出した後の振り返りとフィードバックをおろそかにしないことです。PDCA の A（改善）まで回さないと、リリースした時点で満足して終わってしまいます。見るべきは、出したものが事業に貢献しているかどうかです。

先に書いたマイクロサービスでも、運用費と請求額を並べた数字が、廃止を提案するときの説得力になりました。運用費やシステムの実態に一番近いのはエンジニアです。こうした提案をエンジニアができなければ、コーディングエージェントによる加速度的な開発に組織が耐えられません。

エンジニアにできるのは、待ったをかけることだけではありません。時間がなくて、これまであまり行われてこなかった仕事もあります。ディスカバリー（何を作るかを探る）です。『EMPOWERED』では、プロダクトチームの仕事をディスカバリーとデリバリー（実際に作る）の2つに分けて捉えています。エージェントのおかげで、デリバリーにかかる時間は減りました。浮いた時間で、エンジニアもディスカバリーを手伝えます。ほかのチームが効果を見込んで試したいことがあれば、試せる形にするのを手伝います。先に書いたカスタマーサクセスチームの BI ツールでデータベースとの連携を手伝ったのも、その1つです。

## まとめ

コーディングエージェントで作る速さが上がった今、見るべきは開発の速さだけではありません。足した機能が事業に貢献しているか、組織のどこにボトルネックがあるかを、実態と数字で確かめる必要があります。手を入れる前に測れるものは測り、測れないものは出した後に測ります。この記事の事例では障害がきっかけになったものも含めて、どれも実態を調べ、実績から学んでから手を動かしてきました。『シンプリシティ』の「方向を見定め、一歩進み、学ぶ（Orient, Step, Learn）」は、この進め方と重なります。違和感のあるところから方向を見定め、シンプルな一歩を踏み出し、その結果を振り返って学ぶサイクルです。

事業生産性をエンジニアリングするとは、方向を見定め、一歩進み、学ぶサイクルを全体最適に向けて回し続けることだと考えています。はじめの一歩としては、チームのメンバーが苦労していることや繰り返している作業を無くす全体最適から始めることをおすすめします。売上増加への貢献や、満足度を上げる取り組みのように数字に表れにくい価値の扱いは、別の記事で考えてみたいです。
