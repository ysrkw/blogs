## タイトル候補

1. 組織とマネジメントとソフトウェアアーキテクチャ（採用）
2. 組織にもアーキテクチャがある
3. なぜ業績が悪いと組織を変えるのか ── エンジニアが組織を“設計”として読む話（不採用：ネガティブワード）

## リード文の方向性

- 開発やコードに集中している現状を肯定する。ただし、それだけだと見えないものがある
- マネージャーはなぜあの動きを求めてくるのか／なぜ組織は組み替えられるのか、という問いを置く
- 本記事の主張をワンライナーで予告：組織とマネジメントは、どちらもソフトウェアアーキテクチャと同じ言葉で読める
- 読み終えた後で得られる視点を提示：自分の仕事の位置と、マネージャーの動きが地続きに見えてくる

## 構成

### H2: 開発の外側を見るとき、エンジニアは何に困るか

- 要点: 読者の現状を肯定しつつ、視差を広げるときの「困り」を言語化して入口にする
- 含める要素:
  - ジュニア〜中堅が開発・コードに集中する傾向（それ自体は悪くない）
  - 組織やマネジメントが「別世界の話」に見える違和感
  - 本記事の主張のワンライナー予告
- 一次体験・具体例: 自分も「マネージャーに向いていない」と思っていた頃、組織の話を遠いものと感じていた（主役にしない、軽く触れる程度）
- 参考: 『エンジニアリングが好きな私たちのためのエンジニアリングマネジャー入門』（補助）

### H2: 組織はソフトウェアアーキテクチャと同じ言葉で読める

- 要点: 本記事の中心主張その1。組織側の概念をアーキテクチャの語彙で読み替えるフレームを提示する
- 含める要素:
  - モジュール分割 ↔ チーム分割
  - インターフェース ↔ 役割と責務
  - カップリング ↔ 依存関係・連携コスト
  - リファクタリング ↔ 組織再編・仕組み変更（設計変更による最適化の検証）
- 一次体験・具体例: マネージャー研修や日常の組織議論で「これプログラミングと同じだ」と感じた瞬間を1〜2点（人物名・組織名は出さない）
- 参考: 『チームトポロジー』（補助／詳細は H2-4 で）

### H2: マネジメントはプログラミングの観点で読める

- 要点: 本記事の中心主張その2。マネジメント側の概念もプログラミングの語彙で読み替えられることを示す
- 含める要素:
  - KGI/KPI ↔ 目標とアサーション／テスト
  - レバレッジ ↔ 関数の再利用性・抽象化
  - マネージャーのアウトプット ↔ チームのアウトプット（合成関数としての組織）
  - スプリント／役割 ↔ インターフェース契約と実行サイクル
- 一次体験・具体例: KGI/KPI を部下と設定したときの感覚、マネージャー研修で得た言語化
- 参考:
  - 核: 『HIGH OUTPUT MANAGEMENT』
  - 補助: 『SCRUM BOOT CAMP THE BOOK』

### H2: フレームを使うと、組織変更はこう読める

- 要点: 抽象フレームを実例に当てて、読者に使い方を見せる
- 含める要素:
  - ディスカバリー+デリバリー構造の「カップリングと認知負荷が高い」状態
  - ストリームアラインド+プラットフォームへの「モジュール再分割」
  - その結果（リリース速度・課題分離・認知負荷の低下）をフレームの言葉で説明
- 一次体験・具体例: チームトポロジー導入の経験。構造の話に留め、製品名・チーム名は出さない
- 参考:
  - 核: 『チームトポロジー』
  - 補助: 『EMPOWERED』

### H2: 視差が広がると、自分のポジションが見える

- 要点: フレームを持つと読者にどんな変化が起きるかを着地として示す。連載の次回予告へ繋ぐ
- 含める要素:
  - マネージャーの求める動きが「設計上の必然」として読めるようになる
  - プレイヤーのままでもマネージャーを助けるポジションが取れる
  - 【次回予告】AIエージェント＝探索の自動化。人がどこに集中すべきかという問い
- 一次体験・具体例: テックリードとしてプレイヤーに戻った今、視点を持っているからこそ動けている感覚
- 参考:
  - 補助: 『エンジニアリングが好きな私たちのためのエンジニアリングマネジャー入門』
  - 補助: 『ワイズカンパニー: 知識創造から知識実践への新しいモデル』（AI時代の問いと接続）

## まとめで伝えたいこと

- 組織・マネジメント・ソフトウェアアーキテクチャは同じ言葉で読める
- 視差が広がると、自分の仕事の位置とマネージャーの動きが地続きに見える
- 開発の外側を見ることは、キャリアの選択肢を広げる方向の話であってマネージャーになる話ではない
- 次回：AIエージェント時代に、この視差を持つ意味

## ボツ案・脇道メモ

- AIエージェント＝探索の自動化の詳細（本記事では次回予告に留める／別記事へ）
- 「マネージャーに向いていない」自己開示を中心軸に据えた版（思考フレーム提示という本記事の狙いとズレるため不採用）
- 「業績が悪いと組織を変える」という入口（ネガティブ寄りのため不採用、リファクタリングの比喩は H2-2 で活かす）
- 製品名・チーム名を出す版（社内寄りでも今回は構造の話に抽象化する方針）
